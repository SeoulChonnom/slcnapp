그래서 **기존 모델을 크게 바꾸지 않고 확장할 수 있다.**

## 2. "다녀오기 전" 모델링

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. DRAFT 임장 재사용 (권장)** | 계획 날짜를 `visitedAt`으로 하는 DRAFT 임장을 만들고, 매물을 미리 등록한다. 다녀온 뒤 같은 임장에 문답과 사진을 채운다 | BE 변경이 적다. 계획과 기록이 자연스럽게 이어진다. 기존 "미완료 요약"이 그대로 "아직 안 다녀온 매물"을 보여준다 | 계획 단계에서도 `name`(동·호수)을 넣어야 한다. 임시값("미정")을 허용할지 정해야 한다. `visitedAt`이 "방문일"과 "예정일" 두 뜻을 갖는다 |
| B. 별도 `InspectionPlan` 엔티티 | 계획 → 임장 변환 API | 의미가 명확하다 | BE·FE 작업량이 크다. 데이터가 중복되고 동기화해야 한다 |

→ **A안**으로 하고, 필요하면 임장에 `planned: boolean` 정도만 추가해 목록에서 "예정" 배지를 구분한다.

## 3. 데이터 · API 설계 (BE `slcnapp` 협의 필요)

### 3.1 매물에 위치 필드 추가

```text
ViewedProperty
  + roadAddress      string | null   // 행안부 도로명주소 API로 확정한 주소 (저장 가능)
  + latitude         number | null   // SGIS 지오코딩 WGS84 결과 (저장 가능)
  + longitude        number | null
  + geoSource        'JUSO_SGIS' | null  // 출처 추적 (약관 감사 대비)
  + kakaoPlaceId     string | null   // 선택. 카카오에서 저장 가능한 유일한 필드
```

- 좌표는 **반드시 공공 API 출처만** 저장한다. 카카오나 네이버 좌표는 저장하지 않는다(02 문서 §1).
- 같은 단지의 매물들은 좌표가 같다. 순서를 정할 때 **단지 단위로 묶어** 하나의 지점으로 다룬다.
- 지역(`InspectionArea`)에는 좌표를 넣지 않는다. 지도 중심은 매물 좌표의 bounds로 계산한다.

### 3.2 매물 위치 입력 흐름

```text
[사용자] 단지명 "트리마제" 입력
   │
   ├─(1) 카카오 키워드 검색 (FE → BE 프록시 → dapi.kakao.com)   ※ 실시간, 저장 안 함
   │      → 후보 목록(이름·주소)을 화면에만 표시
   │
   ├─(2) 사용자가 후보 선택 → 그 주소 문자열로
   │      행안부 도로명주소 검색 API 재조회 (BE)               ※ 저장 가능 데이터로 "다시 확정"
   │
   ├─(3) 확정된 도로명주소 → SGIS geocodewgs84 (BE)            ※ 저장 가능
   │
   └─(4) roadAddress / latitude / longitude 저장 (+ kakaoPlaceId)
```

- (1)을 빼고 처음부터 행안부 주소 검색만 쓸 수도 있다. 하지만 **단지명으로 검색할 수 없어서** 사용성이 크게 떨어진다.
- 대안: (1) 없이 "주소 검색 팝업(행안부)"만 제공하고 단지명은 사용자가 따로 입력한다. 약관 리스크는 0이고 UX는 한 단계 늘어난다.
- 카카오 장소 ID로 단건 조회하는 공식 API는 확인하지 못했다. 그래서 "ID만 저장하고 매번 다시 조회"하는 순수 카카오 방식은 **구현할 수 있는지 불확실**하다. 이것도 공공 API를 주 경로로 삼는 이유다.

### 3.3 BE 프록시 엔드포인트 (예시)

| 메서드 | 경로 | 외부 호출 | 저장 |
|---|---|---|---|
| GET | `/geo/places?query=` | 카카오 키워드 검색 | ❌ |
| GET | `/geo/addresses?keyword=` | 행안부 도로명주소 검색 | (호출자가 선택) |
| POST | `/geo/geocode` | SGIS 지오코딩 | (매물 저장 시) |
| POST | `/inspection-visits/{visitId}/route` | 카카오 도보 경로 (구간 분할) | ❌ 응답만 전달 |

- **REST 키는 FE에 두지 않는다.** 카카오 REST 키, SGIS secret, 행안부 승인키는 모두 BE에 둔다. FE에는 **카카오 JavaScript 키**만 둔다(도메인 제한).
- BE에서 사용자 식별자를 빼고 외부로 보낸다(02 문서 §2.3).
- 쿼터를 보호하려고 사용자별 rate limit을 둔다(예: 경로 요청 분당 10회).
  → **04 문서 §6.5에서 철회.** 2인 서비스이고, 카카오 유료 설정을 끄면 `429`가 곧 상한이다.

## 4. 방문 순서 추천 알고리즘 (자체 구현)

- 입력: 출발지 S(사용자가 고른 역이나 주소), 지점 집합 P(단지별로 묶은 좌표, 보통 3~10곳), 도착지 E(선택, 없으면 끝점 자유).
- 거리: 하버사인 직선거리 × 보정계수(도심 도보 약 1.2~1.4). API를 부르지 않아서 쿼터 0, 저장 가능, 즉시 계산된다.
- 해법
  - |P| ≤ 8: **전수 탐색** (8! = 40,320가지, 브라우저에서 수 ms)
  - |P| > 8: **최근접 이웃으로 초기해를 만들고 2-opt로 개선**. 10~20곳에서 최적해와 보통 수 % 차이다.
- 위치: `src/domains/inspection/utils/route-order.ts` 같은 **순수 함수**로 두고, 단위 테스트로 검증한다. BE로 옮겨도 로직은 같다.
- 결과(방문 순서)는 우리가 계산한 것이므로 **매물 `sortOrder`로 저장할 수 있다.** 기존 정렬 기능(api.md §6)을 그대로 쓴다.
- 왜 API 기반 최적화를 쓰지 않는가: TMAP 경유지 최적화는 무료 한도가 일 1~50건이고 자동차 기준이다. 걸어서 수백 m~수 km 범위에서는 직선거리 근사로도 순서가 거의 같다.

## 5. 도보 경로 표시 — 호출량과 비용

- 카카오 도보 API는 한 번에 **출발 + 경유 5 + 도착 = 최대 7점**을 받는다. 지점이 k개면 호출 수는 `ceil((k-1)/6)`회다.
  - 예: 출발역 + 단지 6곳 = 7점 → **1회** / 출발역 + 단지 10곳 = 11점 → **2회**
- 저장할 수 없으므로 "경로 보기"를 누를 때마다 다시 호출한다(02 문서 §1.6).

| 가정 | 일일 호출 |
|---|---|
| 사용자 5명 × 하루 4회 경로 보기 × 평균 1.5회 호출 | **30건** |
| 사용자 50명 × 하루 6회 × 2회 | 600건 |
| 무료 한도 | **1,000건/일** (초과 시 건당 10원, 또는 유료 미설정이면 429 차단) |

→ 지금 서비스 규모라면 **무료 한도의 3% 수준**이다. 50명 규모까지도 무료로 운영할 수 있다.
지도 SDK 로드(일 30만 건 무료)는 사실상 제한이 없다.

**UX 원칙**
1. 기본 화면은 **번호 마커 + 직선 연결선 + 추정 도보 시간**(직선 × 보정계수 ÷ 4.5km/h)으로 보여준다. API 호출 0회.
2. "실제 경로 보기"를 누르면 도보 API를 불러와 폴리라인과 실제 시간으로 바꾼다.
3. `429`나 오류가 나면 직선 표시를 유지하고 토스트로 알린다.
4. 화면 하단에 카카오 로고와 데이터 출처(행안부, SGIS)를 표기한다.

## 7. 단계별 계획 · 난이도

| 단계 | 범위 | 외부 API | BE 작업 | FE 작업 | 난이도 | 사용자 가치 |
|---|---|---|---|---|---|---|
| **0** | 키 발급, 약관 확인 질의(02 문서 §6), 화면 설계 | — | — | — | 하 | — |
| **1** | 매물 주소 입력 + 좌표 저장 + 지도에 마커 표시 | 카카오 지도 SDK, 행안부, SGIS (+ 카카오 키워드 검색) | 컬럼 추가, 지오코딩 프록시 | SDK 로더, 지도, 주소 검색 UI | 중 | 동선을 한눈에 파악 |
| **2** | 방문 순서 추천 + 직선 연결선 + 추정 시간 + 순서를 `sortOrder`로 저장 | 없음 | (없음, 기존 정렬 API) | 알고리즘 + 테스트, UI | 하~중 | "어디부터 갈지" 해결 |
| **3** | 실제 도보 경로선 · 시간 | 카카오 도보 경로 | 경로 프록시(구간 분할) | lazy 호출, 폴백 | 중 | 정확한 일정 계획 |
| 4 (선택) | 지역 사이 대중교통, 출발지를 현재 위치로 | 카카오 대중교통, Geolocation | 위치정보법 검토 결과에 따라 | | 중~상 | 하루에 여러 지역 임장 |

**종합 판단**
- 기술적 실현 가능성: **높음.** 필요한 API가 모두 있고, 무료 한도 안에서 운영할 수 있다.
- 법적 실현 가능성: **조건부 높음.** "좌표는 공공 API 출처만 저장, 카카오 데이터는 실시간 사용, GPS 미사용"을 지키면 알려진 리스크를 피할 수 있다.
- 가장 큰 불확실성: ① 카카오의 저장 정책 해석(회색지대인 사용자 확정 주소) ② SGIS·행안부 운영 조건 ③ 카카오 도보 API가 출시 3개월 된 신규 API라는 점(정책이나 스펙이 바뀔 수 있음 → TMAP을 예비로 둔다).
