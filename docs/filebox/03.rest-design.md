# FileBox REST 작업계획

## 목적

이 문서는 `docs/filebox/01-spec-design.md`, `docs/filebox/01-spec-design-implement.md`,
`docs/filebox/02.aggregate-design.md`, `docs/filebox/02.aggregate-design-implement.md`를 기준으로
`slcn-rest` 모듈에서 필요한 변경 범위와 검증 계획을 정리한다.

Spec과 Aggregate 단계에서 Travel/Trip의 파일 참조는 이미 FileBox 중심으로 전환되었다. REST 단계의 목표는 HTTP 어댑터가 새 공개 DTO 계약을 올바르게 통과시키고,
old file contract가 API 테스트나 요청 예시에 남지 않게 정리하는 것이다.

## 분석 기준과 가정

- FileBox 자체는 외부 생성/수정/삭제 API를 제공하지 않는다.
- Travel/Trip API 요청의 `files` 필드가 FileBox item 목록의 유일한 외부 입력 지점이다.
- FileBox owner 생성, item id 생성, target/role/file type 검증은 `slcn-aggregate` 책임이다.
- `slcn-rest`는 HTTP path/query/body를 Facade/Logic 호출로 연결하는 얇은 어댑터로 유지한다.
- REST 단계에서 새 도메인 규칙을 Resource에 중복 구현하지 않는다.
- 현재 `TravelCdo`, `TravelUdo`에는 Bean Validation 어노테이션이 없으므로 Travel 검증은 기존처럼 aggregate 예외 응답으로 처리한다.
- 현재 `TripCdo`는 Bean Validation 어노테이션과 `files @Valid`를 이미 가진다.

## 현재 상태 확인

### 컴파일과 테스트

확인 결과:

```text
./gradlew :slcn-rest:compileJava
BUILD SUCCESSFUL
```

```text
GRADLE_USER_HOME=/tmp/gradle-home ./gradlew :slcn-rest:test
BUILD SUCCESSFUL
```

### 현재 Resource 구조

`TravelResource`는 기존 엔드포인트를 유지하면서 `TravelLogic`에 DTO를 그대로 위임한다.

- `GET /travels`
- `GET /travels/{travelId}`
- `POST /travels`
- `PUT|PATCH /travels/{travelId}`
- `DELETE /travels/{travelId}`

`TripResource`도 기존 엔드포인트를 유지하면서 `TripLogic`에 DTO를 그대로 위임한다.

- `GET /trips`
- `GET /trips/{tripId}`
- `GET /trips/quiz/{tripId}`
- `GET /trips/quiz/check?tripId=&optionId=`
- `POST /trips`

따라서 현재 production Resource 코드에는 FileBox 전환 때문에 즉시 필요한 시그니처 변경이 없다. Spec Facade와 Aggregate Logic이 이미 새 DTO를 사용하고 있고,
REST compile도 통과한다.

### old contract 잔존 여부

아래 검색 기준으로 `slcn-rest/src/main/java`, `slcn-rest/src/test/java`를 확인했다.

```text
TravelPhoto|TravelTag|TravelPlaceCdo|coverPhotoId|logoFileId|firstMapFileId|secondMapFileId|getTravelDayId|getTravelPlaceId
```

결과:

- REST production/test 코드에 old contract 문자열 잔존 없음.
- 기존 REST 단위 테스트는 대부분 Resource가 Logic에 위임하는지만 확인한다.
- 현재 테스트만으로는 HTTP JSON 계약에서 `files`, `targetType`, `role`, `placeKey`, `date`가 올바르게 역직렬화되는지 검증하지 못한다.

## REST 변경 필요 여부

### Production 코드

현 시점에서 필수 production 변경은 없다.

유지할 방향:

- FileBox 전용 `FileBoxResource`를 만들지 않는다.
- FileBox item 검증을 `TravelResource` 또는 `TripResource`에 중복 구현하지 않는다.
- Travel/Trip Resource는 기존 Facade 구현체로 유지한다.
- CommonExceptionHandler는 기존 `BusinessException`, `MethodArgumentNotValidException`, `HttpMessageNotReadableException` 매핑을 유지한다.

검토만 필요한 항목:

- 추후 `TravelCdo`, `TravelUdo`, `FileBoxItemCdo/Udo`에 Bean Validation 어노테이션을 추가하면 `TravelResource`의 request body에도 `@Valid` 추가를 검토한다.
- 이번 단계에서는 Travel DTO에 검증 어노테이션이 없으므로 `@Valid`만 추가하는 변경은 실효성이 낮다.
- Trip 생성은 이미 `@RequestBody @Valid TripCdo`로 선언되어 있어 `files` null 같은 기본 요청 오류는 REST handler를 통해 400으로 응답된다.

### 테스트 코드

필수 변경은 테스트 보강이다.

현재 `TravelResourceTest`, `TripResourceTest`는 직접 DTO 객체를 만들어 Resource 메서드를 호출한다. 이 방식은 컴파일 안정성은 확인하지만, JSON 요청 계약 변경은 검증하지 못한다.

REST 단계에서는 아래 중 하나를 선택한다.

권장:

- 기존 단위 위임 테스트는 유지한다.
- Travel/Trip 각각에 `@WebMvcTest` 기반 JSON 요청 테스트를 추가한다.
- ObjectMapper로 실제 request JSON을 역직렬화하고 Resource까지 도달하는지 검증한다.

단순 대안:

- Resource 단위 테스트에 `files`가 포함된 DTO fixture를 추가한다.
- 단, 이 방식은 JSON enum 값, nested list, Bean Validation handler까지 확인하지 못하므로 회귀 방지 효과가 제한적이다.

## 구현 계획

### 1단계: REST 코드 영향도 재확인

작업:

- `slcn-rest` production 코드에서 삭제된 old contract 참조를 재검색한다.
- `TravelResource`, `TripResource`가 최신 Facade 시그니처를 구현하는지 컴파일로 확인한다.
- FileBox 전용 Resource가 필요하지 않음을 문서화한다.

완료 기준:

- `./gradlew :slcn-rest:compileJava` 성공
- old contract 검색 결과 없음

### 2단계: Travel REST 계약 테스트 보강

작업:

- `TravelResource` 대상 JSON 요청 테스트를 추가한다.
- 생성 요청에서 `files[].targetType`, `files[].role`, `travelDays[].date`, `places[].placeKey`가 DTO로 역직렬화되어 `TravelLogic.registerTravel`에 전달되는지 검증한다.
- 수정 요청에서 기존 item `id`와 신규 item id 없음 케이스가 `TravelLogic.modifyTravel`에 전달되는지 검증한다.
- old request field인 `coverPhotoId`, day/place `photos`를 사용하는 fixture를 제거한다.

완료 기준:

- Travel REST 테스트에서 새 FileBox payload를 사용한다.
- Travel Resource가 FileBox 검증을 직접 수행하지 않고 Logic에 위임한다.

### 3단계: Trip REST 계약 테스트 보강

작업:

- `TripResource` 대상 JSON 요청 테스트를 추가한다.
- 생성 요청에서 `files` 기반 `LOGO`, `FIRST_MAP`, `SECOND_MAP` payload가 `TripLogic.registerTrip`에 전달되는지 검증한다.
- `files` 누락 시 `TripCdo.@NotNull`과 `CommonExceptionHandler`를 통해 400 응답이 나는지 검증한다.
- old request field인 `logoFileId`, `firstMapFileId`, `secondMapFileId` fixture를 제거한다.

완료 기준:

- Trip REST 테스트에서 새 FileBox payload를 사용한다.
- Trip Bean Validation 실패가 기존 error response 형식으로 응답된다.

### 4단계: 예외 응답 경계 확인

작업:

- aggregate의 FileBox 검증 실패가 `BusinessException` 계열이면 기존 `CommonExceptionHandler.businessException` 경로로 처리되는지 확인한다.
- malformed enum 값, 잘못된 JSON body는 `HttpMessageNotReadableException`으로 400 응답되는지 확인한다.
- Bean Validation 실패는 기존 `MethodArgumentNotValidException` 테스트를 유지한다.

완료 기준:

- FileBox 검증 실패를 처리하기 위해 REST 전용 예외 타입을 새로 만들지 않는다.
- 기존 공통 에러 응답 계약을 유지한다.

- REST 테스트 통과
- Spec/Aggregate/REST 조합 테스트 통과
- REST 코드와 테스트에서 old contract 잔존 없음
- 구현 결과를 `docs/filebox/03.rest-design-implement.md`에 기록

## 위험 요소와 결정 사항

### FileBox API 추가 금지

FileBox는 Travel/Trip 요청 처리 과정에서 내부적으로 생성/동기화되는 aggregate다. REST 모듈에 `/file-boxes` 같은 API를 추가하면 다음 문제가 생긴다.

- Spec 설계의 “FileBox 자체는 외부 API로 생성, 수정, 삭제하지 않는다”는 원칙과 충돌한다.
- FileBox item의 target 존재 검증을 Travel/Trip 맥락 없이 수행해야 해서 검증 책임이 분산된다.
- FE가 FileBox와 Travel/Trip을 별도 순서로 호출해야 하므로 owner lifecycle 일관성이 약해진다.

따라서 REST 단계에서는 FileBox 전용 Resource를 만들지 않는다.

### Resource에 검증 중복 금지

Travel/Trip별 target/role/file type 정책은 aggregate Logic에 이미 구현되어 있다. Resource에 같은 검증을 추가하면 정책 중복과 불일치 위험이 생긴다.

REST에서 담당할 검증은 HTTP 레벨에 한정한다.

- JSON body 파싱 가능 여부
- Bean Validation이 걸린 DTO의 기본 형식
- path/query parameter 전달

### Travel Bean Validation 도입 여부

Trip은 DTO 수준 기본 검증이 이미 있다. Travel은 현재 DTO에 Bean Validation 어노테이션이 없으므로 REST 단계에서 `@Valid`만 추가해도 실질 검증 효과가 없다.

Travel DTO 검증을 강화하려면 별도 Spec 변경으로 처리한다.

- `TravelCdo`, `TravelUdo`, `FileBoxItemCdo/Udo`에 어노테이션 추가
- `TravelResource` request body에 `@Valid` 추가
- 기존 aggregate 예외 메시지와 REST validation 메시지 충돌 여부 검토

이번 REST 계획의 기본 범위에는 포함하지 않는다.

### HTTP 상태 코드

현재 Resource는 생성 성공도 `200 OK`를 반환한다. REST 관점에서는 `201 Created`가 더 자연스럽지만, 기존 API 계약 변경에 해당한다.

이번 FileBox 전환의 직접 목표가 아니므로 상태 코드는 유지한다. 상태 코드 변경은 별도 API 계약 변경으로 다룬다.

## 테스트 계획

### 단위 테스트 유지

- `TravelResourceTest`
    - 목록/상세/생성/수정/삭제가 `TravelLogic`에 위임되는지 확인
- `TripResourceTest`
    - 목록/상세/퀴즈/생성이 `TripLogic`에 위임되는지 확인
- `CommonExceptionHandlerTest`
    - BusinessException, validation, malformed request, unhandled exception mapping 확인

### JSON 계약 테스트 추가

Travel:

- 생성 JSON의 `files`가 `TravelCdo.files`로 들어간다.
- 수정 JSON의 기존 item `id`가 `TravelUdo.files`로 들어간다.
- `targetType=TRAVEL_PLACE`의 `targetId`가 `placeKey`와 같은 문자열로 전달된다.
- old `coverPhotoId` 없는 fixture를 기준으로 테스트한다.

Trip:

- 생성 JSON의 role별 files가 `TripCdo.files`로 들어간다.
- `files` 누락 시 400 응답을 확인한다.
- 잘못된 enum 값이면 400 응답을 확인한다.
- old 직접 파일 ID 없는 fixture를 기준으로 테스트한다.

## 완료 기준

REST 단계 완료 기준은 다음과 같다.

- `slcn-rest` production compile 성공
- `slcn-rest` 테스트 성공
- Spec/Aggregate/REST 조합 테스트 성공
- REST production/test 코드에 old file contract 참조 없음
- FileBox 전용 REST API가 추가되지 않음
- Travel/Trip API 테스트 fixture가 `files` 기반 요청으로 정리됨
- REST Resource가 aggregate 검증 책임을 중복하지 않음

## 결론

현재 `slcn-rest` production 코드는 FileBox 전환으로 인한 필수 수정이 거의 없다. `TravelResource`와 `TripResource`는 이미 새 Spec DTO와 Aggregate Logic 시그니처로 컴파일된다.

REST 단계의 핵심은 새 API JSON 계약을 테스트로 고정하고, old request payload가 문서/테스트에 남지 않게 정리하는 것이다. FileBox는 별도 REST API로 노출하지 않고,
Travel/Trip 요청의 `files` 필드를 통해서만 다룬다.
