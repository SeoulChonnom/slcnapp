# 임장 기록 및 매물 관리 기능 요구사항 명세서

## 1. 개요

### 1.1 목적

사용자가 특정 지역을 임장한 후, 해당 지역에 대한 전체적인 인상과 실제로 확인한 여러 매물의 정보를 체계적으로 기록하고 관리할 수 있는 기능을 제공한다.

주요 기록 대상은 다음과 같다.

- 임장한 지역
- 임장 일자 및 지역에 대한 전체 평가
- 임장 중 확인한 여러 매물
- 각 매물의 단지/건물 정보
- 각 매물에 대한 상세 평가
- 각 매물별 사전 정의 문답
- 임장 및 매물 사진
- 태그를 활용한 분류
- 매물별 관심도

동일한 지역은 여러 번 임장할 수 있으며, 하나의 임장에서는 여러 단지 또는 건물의 여러 매물을 확인할 수 있다.

---

# 2. 도메인 구조

전체 데이터 관계는 다음과 같다.

```text
임장 지역(InspectionArea)
        │
        │ 1:N
        ▼
임장 기록(InspectionVisit)
        │
        ├────────────────┐
        │                │
        │ 1:N            │ 1:N
        ▼                ▼
임장 사진          확인 매물(ViewedProperty)
                         │
                         ├────────────────┐
                         │                │
                         │ 1:N            │ 1:N
                         ▼                ▼
                    매물 사진         매물 문답

질문(Question)
        │
        │ 1:N
        ▼
질문 버전(QuestionVersion)
        │
        └──────────────── PropertyAnswer
```

---

# 3. 주요 용어 정의

## 3.1 임장 지역

사용자가 임장을 수행한 특정 지역 또는 생활권을 의미한다.

특정 아파트나 오피스텔 등의 개별 단지를 의미하지 않는다.

예:

```text
성수동
잠실
흑석동
마곡
광교
```

사용자는 동일한 임장 지역을 여러 번 방문할 수 있다.

---

## 3.2 임장 기록

특정 날짜와 시간에 특정 지역을 방문한 기록이다.

예:

```text
임장 지역
성수동

임장 일시
2026-09-17 14:00
```

동일한 지역을 다시 방문한 경우 기존 기록을 수정하지 않고 새로운 임장 기록을 생성한다.

---

## 3.3 확인 매물

하나의 임장에서 실제로 확인한 개별 매물을 의미한다.

매물은 특정 단지 또는 건물에 속할 수 있다.

예:

```text
단지/건물명
트리마제

매물명
101동 1203호 / 84A
```

하나의 임장에서는 여러 단지의 여러 매물을 등록할 수 있다.

예:

```text
성수동 임장

├─ 트리마제
│  ├─ 101동 1203호 / 84A
│  └─ 102동 1501호 / 84A
│
└─ 서울숲리버뷰자이
   └─ 105동 803호 / 84B
```

초기 버전에서는 단지 자체를 별도 Entity로 분리하지 않는다.

---

# 4. 임장 지역 관리

## 4.1 임장 지역 저장 정보

임장 지역에는 다음 정보를 저장한다.

| 항목      | 필수 여부 | 설명                                 |
| --------- | --------- | ------------------------------------ |
| 지역명    | 필수      | 임장 지역을 구분하는 이름            |
| 지역 설명 | 선택      | 임장 범위 또는 세부 지역에 대한 설명 |
| 생성일    | 자동      | 최초 등록일                          |
| 수정일    | 자동      | 최종 수정일                          |

예:

```text
지역명
성수동

지역 설명
서울숲 ~ 뚝섬역 주변
```

---

# 5. 임장 지역의 위치 정보

초기 버전에서는 임장 지역의 위도 및 경도를 저장하지 않는다.

지역 식별은 다음 값을 기준으로 한다.

```text
지역명
지역 설명(optional)
```

외부 지도 API에 종속되는 식별자 역시 초기 버전에서는 저장하지 않는다.

향후 지도 기반 임장 이력 조회 등의 기능이 필요할 경우 위도/경도를 추가할 수 있도록 확장 가능하게 설계한다.

---

# 6. 동일 지역 재임장

동일한 지역에는 여러 개의 임장 기록을 생성할 수 있다.

예:

```text
성수동

├─ 2026-09-17 임장
│
└─ 2026-11-03 임장
```

과거 임장 기록은 이후 지역 정보가 변경되더라도 독립된 기록으로 유지되어야 한다.

---

# 7. 임장 기록 관리

## 7.1 임장 기록 저장 정보

각 임장 기록에는 다음 정보를 저장한다.

| 항목        | 필수 여부 | 설명                            |
| ----------- | --------- | ------------------------------- |
| 임장 지역   | 필수      | InspectionArea 참조             |
| 임장 일시   | 필수      | 실제 방문 날짜 및 시간          |
| 전체 메모   | 선택      | 해당 지역 임장에 대한 자유 기록 |
| 재방문 의사 | 필수      | 해당 지역에 다시 임장할 의사    |
| 한줄평      | 선택      | 해당 임장 전체에 대한 간략 평가 |
| 장점        | 선택      | 해당 지역/임장의 장점           |
| 단점        | 선택      | 해당 지역/임장의 단점           |
| 태그        | 선택      | 임장 기록 분류용 태그           |
| 상태        | 필수      | 작성중 / 완료                   |
| 생성일      | 자동      | 생성 시각                       |
| 수정일      | 자동      | 수정 시각                       |

---

# 8. 재방문 의사

재방문 여부는 Boolean이 아니라 Enum 형태로 관리한다.

```text
YES
MAYBE
NO
```

화면 표시 예:

```text
다시 임장하고 싶음
조금 더 고민
재방문하지 않을 예정
```

재방문 의사는 해당 지역 자체의 속성이 아니라 특정 임장 시점에서 사용자가 내린 판단이다.

---

# 9. 임장 일시

방문 날짜와 시간은 하나의 날짜/시간 값으로 저장한다.

예:

```text
2026-09-17 18:30
```

화면에서는 필요에 따라 다음과 같이 표현할 수 있다.

```text
2026.09.17
목요일
18:30
저녁
```

별도의 방문 시간대 값은 기본적으로 저장하지 않는다.

향후 사용자가 정확한 시간을 입력하지 않는 기능이 필요한 경우 다음과 같은 Enum 추가를 고려할 수 있다.

```text
MORNING
AFTERNOON
EVENING
NIGHT
```

---

# 10. 임장 상태 관리

임장 기록에는 다음 상태를 지원한다.

```text
DRAFT
COMPLETED
```

## 10.1 DRAFT

작성 중인 임장이다.

다음 상황에서도 저장할 수 있어야 한다.

- 임장 기본 정보 작성 중
- 일부 매물만 등록된 상태
- 매물 문답 작성 중
- 사진 업로드 중
- 필수 문답이 미완료된 상태

## 10.2 COMPLETED

임장 기록 작성을 최종 완료한 상태이다.

완료 처리 시 등록된 모든 완료 대상 매물의 필수 조건을 검증한다.

---

# 11. 매물 관리

하나의 임장에는 0개 이상의 매물을 등록할 수 있다.

매물은 반드시 특정 임장 기록에 속한다.

---

# 12. 매물 저장 정보

각 매물에는 다음 정보를 저장한다.

| 항목        | 필수 여부      | 설명                                              |
| ----------- | -------------- | ------------------------------------------------- |
| 단지/건물명 | 필수           | 해당 매물이 속한 아파트, 오피스텔, 건물 등의 이름 |
| 매물명      | 필수           | 사용자가 매물을 구분할 수 있는 이름               |
| 매물 메모   | 선택           | 매물에 대한 자유 기록                             |
| 한줄평      | 선택           | 매물에 대한 간략 평가                             |
| 장점        | 선택           | 매물의 장점                                       |
| 단점        | 선택           | 매물의 단점                                       |
| 관심도      | 필수           | 해당 매물에 대한 관심 정도                        |
| 태그        | 선택           | 매물 분류용 태그                                  |
| 상태        | 필수           | 작성중 / 완료                                     |
| 정렬 순서   | 자동/수정 가능 | 임장 내 표시 순서                                 |
| 생성일      | 자동           | 생성 시각                                         |
| 수정일      | 자동           | 수정 시각                                         |

---

# 13. 단지/건물명

임장 지역이 특정 아파트가 아니라 넓은 지역이므로 매물에는 단지 또는 건물 정보를 별도로 저장한다.

예:

```text
단지/건물명
트리마제

매물명
101동 1203호 / 84A
```

다른 예:

```text
단지/건물명
서울숲리버뷰자이

매물명
105동 803호 / 84B
```

초기 버전에서는 단지 또는 건물을 별도의 Entity로 분리하지 않고 매물의 속성으로 저장한다.

향후 단지 자체에 대한 평가가 필요한 경우 별도 Entity로 분리할 수 있다.

---

# 14. 매물명

매물명은 사용자가 직접 입력한다.

예:

```text
101동 1203호 / 84A
205동 501호 / 59B
108동 고층 / 84A
```

초기 버전에서는 동, 호수, 평형, 전용면적 등을 별도 컬럼으로 분리하지 않는다.

향후 매물 비교 및 검색 기능이 고도화되는 경우 구조화된 데이터로 분리할 수 있다.

---

# 15. 매물 관심도

각 매물에는 사용자의 관심도를 기록한다.

관심도는 1~5 범위의 정수로 저장한다.

```text
1
2
3
4
5
```

화면에서는 별점 등으로 표현할 수 있다.

```text
★★★★★ 매우 관심 있음
★★★★☆ 관심 있음
★★★☆☆ 보통
★★☆☆☆ 관심 낮음
★☆☆☆☆ 관심 없음
```

관심도는 문답 또는 장단점과 별개로 사용자가 내리는 종합적인 주관 평가이다.

---

# 16. 매물 상태

각 매물에는 다음 상태를 지원한다.

```text
DRAFT
COMPLETED
```

## 16.1 DRAFT

매물 정보 또는 문답 입력이 완료되지 않은 상태이다.

## 16.2 COMPLETED

필수 정보 및 필수 문답 입력이 완료된 상태이다.

매물 완료 처리 시 해당 매물에 적용된 필수 질문의 응답 여부를 검증한다.

---

# 17. 매물별 문답

문답은 임장 지역이나 임장 기록 전체가 아니라 개별 매물을 기준으로 작성한다.

구조:

```text
InspectionVisit
    └ ViewedProperty
          └ PropertyAnswer
```

예:

```text
트리마제
101동 1203호 / 84A

Q. 거실 채광은 어떤가?
A. 오후에도 상당히 밝았다.

Q. 외부 소음은 어떤가?
A. 창문을 닫으면 거의 들리지 않았다.

Q. 수납 공간은 충분한가?
A. 현관과 안방은 충분하지만 주방은 부족했다.
```

---

# 18. 질문 관리

질문은 독립적으로 관리한다.

관리자는 다음 기능을 사용할 수 있어야 한다.

- 질문 등록
- 질문 수정
- 질문 미사용 처리
- 질문 순서 변경
- 필수 여부 설정
- 질문 타입 설정

기존 답변에서 사용된 질문은 물리적으로 삭제하지 않는다.

---

# 19. 질문 활성화 여부

질문에는 활성 여부를 저장한다.

```text
enabled = true
enabled = false
```

미사용 처리된 질문은 신규 매물 문답에 노출하지 않는다.

단, 과거 매물에 이미 작성된 해당 질문과 답변은 계속 조회할 수 있어야 한다.

---

# 20. 질문 변경 이력 보존

질문 내용 변경으로 인해 기존 임장 또는 매물 기록이 변경되어서는 안 된다.

질문은 다음과 같이 Version으로 관리한다.

```text
Question
    │
    ├─ QuestionVersion v1
    ├─ QuestionVersion v2
    └─ QuestionVersion v3
```

예:

```text
Question #12

v1
거실 채광은 어떤가?

v2
거실 및 방의 채광은 어떤가?
```

기존 매물:

```text
트리마제 101동 1203호
→ Question #12 / Version 1
```

신규 매물:

```text
트리마제 102동 1501호
→ Question #12 / Version 2
```

기존 기록에서는 v1 질문을 그대로 조회할 수 있어야 한다.

---

# 21. 질문 타입

질문은 다음 타입을 지원할 수 있어야 한다.

```text
TEXT
LONG_TEXT
BOOLEAN
SINGLE_SELECT
MULTI_SELECT
NUMBER
RATING
```

초기 버전에서 모든 타입을 사용하지 않더라도 향후 추가 가능하도록 확장 가능한 구조로 설계한다.

---

# 22. 질문 필수 여부

질문에는 필수 여부를 지정한다.

```text
required = true
required = false
```

매물을 `COMPLETED` 처리할 때 필수 질문의 답변 존재 여부를 검증한다.

---

# 23. 질문 순서

질문의 화면 표시 순서는 별도 필드로 관리한다.

```text
sortOrder
```

질문 ID나 생성일자를 표시 순서로 사용하지 않는다.

---

# 24. 작성 중 질문 변경 처리

사용자가 임장 또는 매물 작성을 시작한 이후 질문이 변경되더라도 작성 중인 매물의 질문 구성이 갑자기 변경되어서는 안 된다.

예:

```text
13:00

Q1
Q2
Q3
Q4

사용자가 매물 작성 시작
```

이후 관리자가 Q5를 추가하더라도 기존 작성 중인 매물에 즉시 Q5를 필수로 요구하지 않는다.

이를 위해 매물 작성 시 사용할 질문 버전 목록을 고정한다.

구현 방법은 다음 중 하나를 사용할 수 있다.

```text
QuestionnaireVersion
```

또는

```text
ViewedProperty 생성 시 적용되는 QuestionVersion 목록 Snapshot
```

과거 기록을 언제든 동일한 형태로 복원할 수 있어야 한다.

---

# 25. 태그

임장과 매물은 각각 태그를 가질 수 있다.

태그 자체는 공통으로 관리할 수 있다.

```text
Tag
- id
- name
```

관계:

```text
InspectionVisitTag
- inspection_visit_id
- tag_id
```

```text
ViewedPropertyTag
- viewed_property_id
- tag_id
```

---

# 26. 임장 태그 예시

지역 및 생활권에 대한 특성을 기록하는 용도로 사용한다.

예:

```text
#역세권
#상권좋음
#학군
#한강
#신축많음
#직주근접
#조용함
#교통혼잡
```

---

# 27. 매물 태그 예시

개별 매물의 특성을 기록하는 용도로 사용한다.

예:

# 36. 임장 완료 조건

임장을 완료하기 위해 다음 조건을 만족해야 한다.

1. 임장 지역이 존재한다.
2. 임장 일시가 입력되어 있다.
3. 재방문 의사가 입력되어 있다.
4. 등록된 완료 대상 매물의 필수 문답이 작성되어 있다.
5. 각 완료 매물의 관심도가 입력되어 있다.
6. 완료 대상으로 등록된 매물의 상태가 `COMPLETED`이다.

임장에는 매물이 존재하지 않아도 된다.

예:

```text
성수동 상권 및 생활권만 확인하고 돌아온 임장
```

도 정상적인 임장 기록으로 저장할 수 있어야 한다.

# 37. 매물 완료 조건

매물을 완료하기 위해 다음 조건을 만족해야 한다.

1. 단지/건물명이 존재한다.
2. 매물명이 존재한다.
3. 관심도가 존재한다.
4. 관심도는 1~5 범위이다.
5. 모든 필수 질문에 대한 답변이 존재한다.

조건을 만족하지 않으면 `COMPLETED` 상태로 변경할 수 없다.

# 49. 핵심 비즈니스 규칙

1. 임장 지역은 특정 아파트 또는 특정 건물이 아니라 사용자가 임장한 지역 또는 생활권을 의미한다.
2. 하나의 임장 지역에는 여러 임장 기록을 등록할 수 있다.
3. 동일 지역을 재방문하면 기존 기록을 수정하지 않고 새로운 `InspectionVisit`을 생성한다.
4. 하나의 임장에는 0개 이상의 매물을 등록할 수 있다.
5. 하나의 임장에서는 여러 단지 또는 건물의 매물을 확인할 수 있다.
6. 매물에는 단지/건물명과 매물명을 각각 저장한다.
7. 초기 버전에서는 단지/건물을 별도의 Entity로 관리하지 않는다.
8. 문답은 임장 전체가 아니라 개별 매물에 작성한다.
9. 질문 수정은 기존 매물 답변과 과거 임장 기록에 영향을 주어서는 안 된다.
10. 미사용 질문은 신규 매물에는 노출하지 않는다.
11. 기존 기록에서는 미사용 질문도 계속 조회할 수 있어야 한다.
12. 질문 변경은 새로운 `QuestionVersion`으로 관리한다.
13. 작성 중 데이터는 `DRAFT` 상태로 저장할 수 있다.
14. 필수 문답을 완료한 매물만 `COMPLETED` 처리할 수 있다.
15. 매물별 관심도를 반드시 저장한다.
16. 관심도는 1~5 범위로 제한한다.
17. 임장과 매물은 각각 태그를 가질 수 있다.
18. 임장 사진과 매물 사진은 서로 구분하여 관리한다.
19. 매물 및 사진의 표시 순서는 별도의 `sortOrder`로 관리한다.
20. 기존 답변이 연결된 질문은 물리 삭제하지 않는다.
21. 임장 지역의 위도/경도 및 외부 지도 Place ID는 초기 버전에서 저장하지 않는다.
22. 임장에는 매물이 존재하지 않아도 완료할 수 있다.
23. 같은 단지의 여러 매물을 하나의 임장에서 등록할 수 있다.
24. 향후 단지 자체에 대한 기록이 필요해질 경우 `VisitedComplex` Entity를 추가할 수 있도록 확장 가능하게 설계한다.
